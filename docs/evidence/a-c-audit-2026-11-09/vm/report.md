# Disposable Hyprland VM audit

Source commit `eaabe434519a291dd5f8108014fe7186570e5418`; `hashes.txt` records the source archive and installed wheel SHA-256. `commands.txt`, Dockerfiles and copied scratch scripts preserve the commands and harness. No repository source or tests were modified. Guest and QEMU runner had no network. The first preparation attempt exited 126 because copied scripts lacked executable mode; `prepare-retry.log` records the successful Bash invocation.

The first guest used Ubuntu 26.04, Hyprland 0.53.3, Aquamarine 0.10, Python 3.14, the current installed wheel, official Ubuntu `grim 1.4.0+ds-2build3`, and yad/AT-SPI. `image-versions.txt` records package versions. The existing acceptance script passed all seven checks, exit 0 (`results/desktop-acceptance.json`, `acceptance.log`, screenshot and independent keyboard marker). The unmodified marked suite ran 16 tests: **11 passed, 5 failed, 1,523 deselected**, exit 1 (`results/pytest.log`). Every failure is caused by `grim failed: jpeg support disabled` in default JPEG screenshot or zoom; this is a compatibility finding for this official Ubuntu package, not a skipped or passing test. The lossless PNG acceptance still passed. AT-SPI activated and background tests ran.

Configuration readback probes set scale 1 and 1.25 and keyboard layouts US and German; `results/matrix*` holds before/after monitor and device JSON, command outputs, and screenshots. Reported scale and active keymap matched each setting. These readbacks alone do not establish functional input or coordinate correctness under each combination.

On first guest teardown Hyprland segfaulted in `libaquamarine.so.0.10.0`; compositor exit was 139 (`results/compositor-exit.json`, `vm-run.log`). This is separate from the acceptance result; the VM lifecycle was not clean. This older compositor uses Hyprlang; no Lua compositor was tested.

A second fresh guest used the same official grim package, not a JPEG-enabled replacement. Two attempted download URLs returned 404 (`jpeg-build.log`, `jpeg-build-retry.log`); the matching Ubuntu source package was then fetched but omits `write_jpg.c`, so the JPEG-enabled build failed (`jpeg-build-third.log`). A JPEG-enabled run of the 16 tests was **not achieved**. The second run on the original image independently repeated 11 passed, 5 failed, 1,523 deselected (`retry-jpeg/results/pytest.log`).

The second guest also ran the existing acceptance script separately for all four scale/layout combinations: 1/US, 1/German, 1.25/US, 1.25/German. All four returned exit 0. Each records the independent cursor position, typed shell marker, PNG capture, window identity and close, plus other checks (`retry-jpeg/results/matrix*-acceptance/`). Each combination also has before/after settings and screenshots. This covers the script's specific coordinates and input, not every coordinate, character, or application. The second compositor also segfaulted at teardown with exit 139 (`retry-jpeg/vm-run.log`).

A bounded third guest checked the advertised named seat `Hyprland` and reused one `VirtualKeyboard` connection for three `type_text` calls. Independent `hyprctl -j devices` counts were 3 before, 3 after connection creation, then 4, 5 and 6 after the calls, returning to 3 on connection close (`seat-probe/results/keyboard-growth.json`). Thus device objects accumulate while that connection remains open and were reclaimed on close in this run. The first attempt used `seat0`, which this compositor rejected and reported `Hyprland` as its seat (`retry-jpeg/results/keyboard-growth.json`); it sent no typing. The probe guest's compositor also exited 139. Its runner exits 1 because the general summary expects a desktop acceptance JSON that this probe-only guest intentionally does not produce; its raw guest result was 0 and the separate compositor status was 139 (`seat-probe/vm-run.log`).
